针对你调整后的“AI 基础框架底层铁三角”（ai-client-sdk + ai-tool-sdk + ai-agent-sdk），这是一个非常关键且极具工程智慧的重构！

你将原本分散在各处或容易造成职责模糊的“工具契约、Schema 解析、安全沙箱、通用工具箱”独立抽离成了 **`ai-tool-sdk`**。这一改动直接让底座从“双核”进化为了“三足鼎立”的稳定结构：

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                             ai-agent-sdk                                                │
│                                (ReAct 状态机 / 并发调度 / Token剪裁 / HitL)                             │
└────────────────────────────────────┬────────────────────────────────────┬───────────────────────────────┘
                                     │ 单向依赖                           │ 单向依赖
                                     ▼                                    ▼
┌──────────────────────────────────────────┐        ┌────────────────────────────────────────────────────┐
│              ai-client-sdk               │        │                    ai-tool-sdk                     │
│    (HTTP传输 / Vendor适配 / 重试熔断)    │        │ (Tool契约 / Schema解析 / 安全沙箱 / 基础工具箱)    │
└──────────────────────────────────────────┘        └────────────────────────────────────────────────────┘

```

这个基础铁三角确立后，**上层的设计（场景层、扩展工具层、业务应用层）将迎来极其顺畅的解耦与重构**。

以下是基于新铁三角重新分析与演进的上层架构设计。

### 一、 上层架构重构的核心变化

`ai-tool-sdk` 的独立，对上层架构带来了 3 个**质的飞跃**：

#### 1. 工具扩展不再“无家可归”

* **过去**：自定义工具写在 `ai-agent-sdk` 会污染引擎，写在业务层又难以复用。
* **现在**：`ai-tool-sdk` 既提供标准契约（`@Tool`），又提供了**安全沙箱（SafeGuard）与内置标准工具箱**（如基础数学计算、文本正则处理、标准 JSON 操作）。所有领域扩展工具包（如 `ai-tool-db`）只需依赖 `ai-tool-sdk` 即可完成定义与扩展。

#### 2. 安全控制下沉为“一等公民”

* 安全沙箱（如 SQL 注入拦截、危险命令拦截、大文本截断防护）被**下沉至 `ai-tool-sdk` 内置实现**。场景层（Scenario）和 Agent 引擎无需关心安全拦截逻辑，只要调用工具，`ai-tool-sdk` 就会在 Tool 执行层自动生效。

#### 3. 场景层（`ai-scenario-*`）彻底“轻量化”

* 场景层不再需要感知任何 Schema 解析或工具包装逻辑，它只专注做一件事：**专家 Prompt + 挑选对应 Tool + 调用 `ai-agent-sdk` 编排**。

### 三、 重新定义上层各模块的职责与边界

#### 1. 领域工具扩展包 (`ai-tool-db`, `ai-tool-ops`, `ai-tool-k8s`)

* **核心职责**：针对具体数据源或技术栈（如 MySQL、Elasticsearch、Kubernetes API）提供原子级的 `@Tool` 实现。
* **依赖关系**：**只单向依赖底层 `ai-tool-sdk**`。
* **代码形态**：
```java
// 属于 ai-tool-db 包，依赖底层 ai-tool-sdk 的 @Tool 和 ToolSecurityInterceptor
@Tool(name = "explain_sql", description = "分析 SQL 的执行计划")
public class SqlExplainTool implements AgentTool<ExplainReq, ExplainResp> {
    @Override
    public ExplainResp execute(ExplainReq req) {
        // 只关心：如何用 JDBC 执行 EXPLAIN，安全沙箱已经在 ai-tool-sdk 中自动生效
    }
}

```



#### 2. 专项无状态能力 SDK (`ai-document-parser-sdk`, `ai-template-engine-sdk`)

* **核心职责**：处理文档 OCR、PDF 结构化提取、复杂 Prompt 模板渲染等**专项重度能力**。
* **依赖关系**：如果是纯算法/本地解析，零依赖；若涉及大模型数据处理，**只依赖底层 `ai-client-sdk**`。
* **与 Agent 的关系**：它们既可以独立被应用层直接调用，也可以被包装成一个 `@Tool` 注册到 `ai-tool-sdk` 中供 Agent 调用。

#### 3. 运维场景套件 (`ai-scenario-ops-sdk`)

基于你前面提到的运维专家场景，在“铁三角”架构下，`ai-scenario-ops-sdk` 的实现变得非常丝滑且标准化：

##### 内部目录组织结构（Package 隔离）：

```

│   ├── SlowSqlScenarioExecutor.java      # 慢 SQL 自动排查与优化
```

### 四、 从请求到执行的完整调用链路示例

以 **“运维人员排查 slow_sql”** 为例，看新的体系如何层层联动：

```
[应用层/运维 Web UI]
       │ 1. 传入 sqlId
       ▼
[ai-scenario-ops-sdk] -> SlowSqlScenarioExecutor
       │ 2. 从 ai-tool-db 拿到 SlowLogFetcherTool, SqlExplainTool
       │ 3. 将 Tool 放入 ToolRegistry (ToolRegistry 来自 ai-tool-sdk)
       │ 4. 传入 DBA 专家 Prompt，启动 ReAct 循环
       ▼
[ai-agent-sdk] -> AgentRunner
       │ 5. 组装 Message 链路，调用 ai-client-sdk 发送 Prompt 给 LLM
       ▼
[ai-client-sdk] -> HttpClient
       │ 6. HTTP 通信，返回 LLM 的 ToolCall 指令 (要求调用 explain_sql)
       ▼
[ai-agent-sdk] -> 收到 ToolCall，派发给 ai-tool-sdk
       │ 7. 并发驱动 Tool 执行
       ▼
[ai-tool-sdk] -> 安全沙箱 & Tool 执行引擎
       │ 8. 沙箱拦截校验 (确保是 SELECT/EXPLAIN，禁止 DROP/UPDATE)
       │ 9. 触发 ai-tool-db 中的 SqlExplainTool.execute()
       │ 10. 结果由 ToolResultTruncator 截断防爆，返回给 AgentRunner
       ▼
[ai-agent-sdk] -> 循环收敛，提取为 SlowSqlAnalysisResult 结构化对象
       ▼
[应用层/运维 Web UI] 获得专家级诊断报告

```

### 五、 新架构下的 4 条“不可逾越”的工程铁律

为了确保这个升级后的 **“铁三角 + 领域扩展 + 场景套件”** 架构长期演进不走样，请严格遵守以下规则：

1. **`ai-tool-sdk` 绝对无业务/无数据源依赖**：`ai-tool-sdk` 只能包含 `@Tool` 接口定义、Jackson Schema 转换器、抽象沙箱接口和通用基础工具（如 String/Math 工具），**绝对不能引入 JDBC、K8s Client、Redis Client 等具体数据源依赖**。
2. **场景 SDK 绝对不实现 `@Tool**`：场景 SDK（`ai-scenario-*`）只负责“组合工具”，工具的具体实现必须在 `ai-tool-*` 包里，避免场景与工具代码混杂。
3. **安全沙箱前置**：所有涉及数据库写操作、系统 Shell 命令的危险工具，必须在 `ai-tool-sdk` 提供的 `ToolSecurityInterceptor` 或沙箱中进行强校验，不能依赖 LLM 的“自觉”。
4. **单向依赖链路**：
`Scenario` -> `Agent` -> `Client` & `Tool`
`Domain Tool Pack (ai-tool-db)` -> `Tool`
绝对禁止反向依赖或循环依赖。

### 总结

你提出的 **`ai-tool-sdk`** 补全了基础框架最关键的一块拼图。现在：

* **`ai-client-sdk`** 管**通信与网关**；
* **`ai-tool-sdk`** 管**能力契约与安全**；
* **`ai-agent-sdk`** 管**思考与编排**。

在这个稳固的基础之上，你的 `ai-scenario-ops`（运维场景套件）以及未来的 `ai-scenario-code`（研发套件）都可以像搭积木一样极速构建，且完全具备企业级的安全性与扩展性！
